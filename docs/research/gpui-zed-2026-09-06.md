# GPUI and Zed, mined — 2026-09-06

- Research report, 2026-09-06. Corpus: `zed-industries/zed` at `5a9b955` (shallow, blob-filtered clone,
  2026-09-06) plus its issue tracker. Reaction (`+n`) and comment (`cN`) counts are the API values on that date.
- **Why this corpus.** Zed is the closest live analogue to what ADR-0001 commits us to: a GPU canvas with its own
  scene, its own text stack, its own Wayland client, its own frame loop, shipping to GNOME, KDE, wlroots and
  Hyprland users, on Vulkan, with no widget toolkit underneath. Every problem ADR-0001 lists under *Negative /
  accepted risks* — text, IME, accessibility, fractional scale, scroll physics, driver quirks — Zed has already
  hit in public, with a bug number and often a fix commit. This is not a React Native corpus, so nothing here is
  a parity oracle; it is a **failure-mode oracle**.
- **Where GPUI actually lives.** The paths in the brief are stale at this HEAD. GPUI is now split across
  `crates/gpui` (core: scene, text system, dispatch, a11y, test rig), `crates/gpui_linux`
  (`src/linux/{wayland,x11,headless}/`), `crates/gpui_wgpu` (the renderer and the cosmic-text backend),
  `crates/gpui_platform`, `crates/gpui_macros`, and `crates/scheduler` (the deterministic executor). There is no
  `platform/linux/`, no `platform/blade/`, and Blade has been replaced by wgpu. Section A cites the real paths.
- **Dedupe.** Every candidate was grepped against the title and body of all 257 issues in this repository
  (`gh issue list --state all --limit 700 --json number,title,body`, which returned the whole tracker), and the
  bodies of #20, #23, #26, #42, #51, #54, #65, #70, #242, #249, #292 were read in full. Section D lists what was
  dropped and names the issue that already owns it. Every section E entry carries a `DEDUPE` line.
- **Result:** 23 sub-issues proposed and filed (section E), 21 candidates dropped (section D).

## A. What GPUI does that we can copy as an approach

Each entry: the mechanism and where it lives, why it applies to a Skia/Wayland canvas, and where it lands in our
tree.

### A1. The frame loop is an explicit state machine, and "occluded" is a state in it

- **Mechanism.** `enum FrameLoop { Unconfigured, Ticking, RescheduleRequested, PresentationFailed,
  AwaitingCallback, Scheduled, RetryScheduled, Parked }` in
  `crates/gpui_linux/src/linux/wayland/window.rs:733`, held in an `Rc<Cell<_>>`, alongside
  `enum PresentationState { Unpresented, Presented, RetryBeforeFirstPresent, RetryAfterPresent }` (same file,
  line 663) whose `requires_presentation()` is unit-tested at line 694. Three wakeup sources feed it: the
  `wl_surface.frame` callback, a calloop `Ping` for "the application asked for a frame while parked", and a
  one-shot 60 Hz retry timer (`FRAME_RETRY_INTERVAL = 16_667 µs`,
  `crates/gpui_linux/src/linux/wayland/client.rs:189`). The subtle rule is in `complete_frame()`
  (`window.rs:944`): a surface that has **already presented once** and then fails to present hands pacing back to
  the compositor with a bare `commit` plus a frame callback, rather than burning the retry timer; a surface that
  has **never** presented uses the timer, because no callback is guaranteed. The source comment is explicit:
  "let the compositor pace retries so an occluded window does not keep polling."
- **Why it applies.** ADR-0001 already states that a timer fallback is mandatory because Hyprland sends no frame
  callbacks to a surface on an inactive workspace. What GPUI adds is that the fallback is not a blanket timer: it
  is a state, entered only when a callback cannot be relied on, and left as soon as the compositor is pacing
  again. Our `FrameClock` currently has one fallback timeout and no notion of "the last present failed".
- **Lands in.** `packages/core/src/FrameClock.{h,cpp}`, `WaylandWindow.cpp`, `SkiaVulkanRenderer.cpp`.

### A2. Every request that needs a serial takes a *press* serial, tracked per kind

- **Mechanism.** `crates/gpui_linux/src/linux/wayland/serial.rs`: `SerialKind { DataDevice, InputMethod,
  MouseEnter, MousePress, KeyPress }` in a small map, plus a separate `selection_serial` updated **only** by
  `KeyPress` and `MousePress`, in arrival order so it survives `u32` rollover (unit-tested:
  `test_selection_serial_uses_event_arrival_order_across_rollover`). The comment at `client.rs:2280` states the
  rule: "Record presses only. Requests referencing this serial (popup grabs, interactive moves) are declined when
  given a release serial." `write_to_clipboard` refuses to take ownership when no press serial has been seen yet
  and logs why; popup grabs use `max(MousePress, KeyPress)` and pass no grab at all when that is zero.
- **Why it applies.** `wl_data_device.set_selection`, `xdg_popup.grab`, `xdg_toplevel.move`/`resize`,
  `zwp_text_input_v3`, `wl_pointer.set_cursor` and `xdg_activation_v1.get_activation_token` each need a serial,
  and each is declined silently by the compositor when given the wrong one. We currently pass serials
  positionally from whichever handler happens to be in scope and store none of them.
- **Lands in.** A new `packages/core/src/WaylandSerials.{h,cpp}`, consumed by `WaylandSeat`, `WaylandWindow`,
  `TextInputClient` and the clipboard work of #60.

### A3. The scale factor is baked into the raster key, not carried beside it

- **Mechanism.** `RenderSvgParams { path: SharedString, size: Size<DevicePixels> }`
  (`crates/gpui/src/platform.rs:1280`): the SVG raster key holds the *device* size, so a scale change produces a
  different key and re-rasterisation falls out of a cache miss with no invalidation pass at all. Glyphs do the
  same via `RenderGlyphParams { font_id, glyph_id, font_size, subpixel_variant, scale_factor, is_emoji,
  subpixel_rendering, dilation }`. Bitmap images do **not**, and Zed pays for it: #58438 rasterises Mermaid
  diagrams once at a fixed 2x and never re-renders for the display's DPI.
- **Why it applies.** #51 owns fractional scale and says "the glyph atlas is invalidated and re-rasterized". An
  explicit invalidation pass is a thing that can be forgotten on one of the caches; a scale-keyed cache cannot
  be. We have three raster caches (paragraph, image, gradient shader) and one of them will be missed.
- **Lands in.** `packages/core/src/ImagePipeline.h` (`RenderImageParams`), `TextPipeline.h`,
  `GradientShader.cpp`.

### A4. A frame-scoped layout cache with previous-frame reuse, and an index range as the reuse handle

- **Mechanism.** `LineLayoutCache` (`crates/gpui/src/text_system/line_layout.rs:454`) holds two `FrameCache`s,
  `previous_frame` and `current_frame`. Lookup order is current, then previous (`remove_entry`, which *moves* the
  entry forward and records its key in a `used_lines` vector), then shape. `finish_frame()` swaps the two and
  clears the new current, so an entry survives exactly one frame of non-use. The reuse handle for a skipped
  subtree is `LineLayoutIndex` — a tuple of the `used_*` vector lengths — and `Window::reuse_prepaint(range)`
  replays `previous_frame.used_lines[start..end]` into the current frame **without re-shaping and without even
  hashing the text** (`crates/gpui/src/window.rs:3576`). The same trick generalises: `PaintIndex` and
  `PrepaintStateIndex` (`window.rs:1002`) are tuples of the lengths of about eight parallel arrays, and
  `Window::reuse_paint(range)` extends every one of them from the previous frame at once.
- **Why it applies.** Our `layoutParagraph` (`packages/core/src/TextPipeline.h`) constructs a fresh
  `skia::textlayout::Paragraph` on every call, under one process-wide mutex, relying entirely on Skia's internal
  paragraph cache. Zed #18263 (+37, c25) is what that costs: per-keystroke full relayout making terminal input
  visibly slow. The two-frame swap is 40 lines and needs no eviction policy.
- **Lands in.** `packages/core/src/TextPipeline.{h,cpp}`, `RetainedScene.cpp`.

### A5. Draw order is `1 + max(order of anything I overlap)`, from an R-tree

- **Mechanism.** `crates/gpui/src/bounds_tree.rs`. `Scene::insert_primitive` (`scene.rs:87`) clips the primitive
  to its content mask, discards it if empty, and otherwise asks the tree for an order:
  `find_max_ordering(&bounds) + 1`. Non-overlapping primitives therefore *share* an order and merge into one
  draw call. The tree is an R-tree with `MAX_CHILDREN = 12`, a `max_order` per node for pruning, an O(1) fast
  path (`max_leaf`: if the query overlaps the globally highest-ordered leaf, return immediately — the common UI
  case), no splitting, no deletion, and a wholesale `clear()` each frame. It is brute-force-verified against the
  naive quadratic definition for 1000 seeds (`test_random_iterations`).
- **Why it applies.** Not as a batching mechanism — Skia owns op reordering — but as a **testable definition of
  "safe to reorder"**. Our damage tracking already needs to answer "does this node's damage rectangle interact
  with that one's", and #105 (opacity is a group property) needs to answer "is this subtree self-overlapping".
  The R-tree with a `max_order` prune is the cheap, exact answer, and the brute-force differential test is the
  shape to copy.
- **Lands in.** `packages/core/src/RetainedScene.cpp` (damage merging), `packages/core/tests/SceneTest.cpp`.

### A6. Scroll position is an anchor into an item, not a pixel offset

- **Mechanism.** `crates/gpui/src/elements/list.rs`. `enum PendingScroll { Absolute { item_ix, offset },
  Proportional(PendingScrollFraction { item_ix, fraction }) }` with `enum ScrollAnchor { Absolute, Proportional }`
  (lines 78-110). The documented rule: an absolute anchor "preserves the same pixel offset into the item, which
  keeps visible text stable while content is appended to or removed from that item"; a proportional anchor
  "preserves the same fractional position within the item, which is useful when the whole list is being resized".
  `FollowMode::Tail` and `FollowState` (line 111) form a three-state machine — following, stopped following,
  normal — driving auto-scroll-to-bottom, and it is the single most-tested behaviour in GPUI (12 of the 28 list
  tests).
- **Why it applies.** #292 owns `maintainVisibleContentPosition` on a *prepend*. The harder case is an item
  already in the viewport changing height — an image finishing decode, a paragraph re-wrapping after a resize —
  and a pixel offset cannot express "keep the line the user is reading where it is". An anchor can.
- **Lands in.** `packages/core/src/ScrollController.{h,cpp}`.

### A7. An analytic spring: an exact state-transition matrix, not an integrator

- **Mechanism.** `crates/gpui/src/spring.rs`. `SpringConfig::propagator(delta_time) -> [[f32; 2]; 2]` returns the
  exact 2-by-2 state-transition matrix of a damped harmonic oscillator, branching on the damping ratio
  (under, critical, over, with `CRITICAL_DAMPING_TOLERANCE = 1e-4`). `step()` is one matrix multiply; the doc says
  it "is independent of frame rate and preserves velocity, allowing an interrupted spring to be retargeted
  without restarting it". `step_ramp()` uses a first-order hold for a target that is itself moving, "avoiding the
  frame-rate-dependent lag introduced by treating a dragged target as stationary between frames".
  `settle_time()` returns a conservative analytic settling time (`Duration::MAX` for an undamped spring), and
  `sampled_easing()` converts a spring into a duration plus an easing function.
- **Why it applies.** React Native's `Animated.spring` is specified by its physical parameters, and any
  per-frame integrator makes the trajectory a function of the frame cadence — which on a mixed 60/120/144 Hz
  setup means the same animation looks different on different monitors, and a dropped frame changes the result.
  `settle_time()` is separately valuable: it is what lets a golden test assert "settled" without a wall-clock
  sleep, which the testing gospel forbids.
- **Lands in.** `packages/core/src/` alongside the animated-node work of #19, #75 and #129; the analogous closed
  form for scroll deceleration is already in `ScrollPhysics.cpp` (see D14).

### A8. Client-side decorations are an inset, and the button layout is read from the desktop

- **Mechanism.** `crates/gpui_linux/src/linux/wayland/window.rs`. `request_decorations()` (line 2057) negotiates
  `zxdg_toplevel_decoration_v1`, and when the manager is absent — the GNOME/Mutter case — logs "the Wayland
  server does not support them. Falling back to client-side decorations" and pins `WindowDecorations::Client`.
  Client-side decorations are *intrusive*: `client_inset: Option<Pixels>` shrinks the rendered area inside the
  surface, and two helpers do the arithmetic — `inset_by_tiling(bounds, inset, tiling)` (line 2280), which drops
  the shadow gutter on any edge that is tiled, and `compute_outer_size` (line 2254), which adds the insets back
  because "the configuration event is in terms of the window geometry, which we are constantly updating to
  account for the client decorations". `set_window_geometry` is re-issued after every ack with
  `.map_size(|v| if v <= 0 { 1 } else { v })` because a zero geometry is a protocol error. The opaque region is
  set **only** under server-side decorations, with the comment "rounded corners make this rectangle API hard to
  work with. As this is common when using CSD, let's just disable this API." Button order comes from the desktop:
  `WindowButtonLayout::parse("close,minimize:maximize")` (`crates/gpui/src/platform.rs:619`) parses GNOME's
  `button-layout` setting, deduplicates, and errors only when nothing valid remains;
  `PlatformWindow::on_hit_test_window_control` lets the drawn titlebar declare which region is a control.
- **Why it applies.** We draw everything, so under GNOME we draw the titlebar, the shadow, the resize gutters and
  the buttons, or the window has none. Nothing in the tracker owns this today.
- **Lands in.** `packages/core/src/WaylandWindow.{h,cpp}`, `ToplevelState.h`, `RetainedScene.cpp`.

### A9. The adapter is chosen to match the compositor's GPU, not to be the fastest

- **Mechanism.** `detect_compositor_gpu()` (`crates/gpui_linux/src/linux/wayland/client.rs:~1315`) opens a
  **second, throwaway** Wayland connection, binds `zwp_linux_dmabuf_v1` at version 4, calls
  `get_default_feedback`, roundtrips once, reads `MainDevice { device }` as a native-endian `dev_t`, resolves it
  through sysfs to PCI vendor and device identifiers (`compositor_gpu_hint_from_dev_t`,
  `crates/gpui_linux/src/linux/platform.rs:1225`), and drops the connection. That hint then biases adapter
  selection.
- **Why it applies.** `SkiaVulkanRenderer::selectPhysicalDevice` (line 303) prefers
  `VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU`. On a hybrid laptop where the compositor renders on the integrated GPU,
  that choice costs a cross-device buffer copy every frame, wakes the discrete GPU for a text editor, and is
  exactly Zed #52281 and #61439.
- **Lands in.** `packages/core/src/SkiaVulkanRenderer.cpp`.

### A10. `dirty_at` to `present_end` is the latency, and a hang is a rule over an event journal

- **Mechanism.** `crates/gpui/src/profiler/journal.rs`. `PresentedFrame::dirty_to_present_duration()` is
  `present_end - dirty_at`: from the *first invalidation of that frame generation* to platform submission, not
  from the start of the draw. `FrameDirtyAccumulator` records `dirty_at` only on the clean-to-dirty edge and
  counts how many invalidations coalesced. `InputTiming { kind, start, end, caused_invalidation }` records
  whether an input dispatch actually dirtied anything. Foreground time is modelled as intervals sealed by an
  `IntervalBoundary::{Presented, Idle}`, with `occupancy()`, `busy_fraction()`, and a `Discontinuity { lost }`
  entry so a consumer cannot infer a boundary across a gap in the ring. On top of that,
  `crates/gpui/src/profiler/hang.rs` defines a hang **after the fact** with two rules: `HangTrigger::Threshold`
  (one event blocked the foreground for at least the threshold) and `HangTrigger::Budget` ("an interval whose
  total foreground spend reached the frame budget also counts, even when no single event crossed the threshold:
  many small pieces of work can drop a frame as thoroughly as one long stall"). The benchmark harness expresses
  regression the same way: `BenchReport::budget_overruns(t) = ceil((t - budget) / budget)`, "a synthetic proxy
  for missed frames" (`crates/gpui/src/app/bench_context.rs`).
- **Why it applies.** #20's gate is p95 frame time and #124's is native-driver frame cost; neither measures the
  number a user feels, which is Zed #26900's "at least four frames between moving the pointer and seeing the
  result". `dirty_to_present` is that number, and we already have `wp_presentation` feedback bound to supply
  `present_end` honestly.
- **Lands in.** `packages/core/src/FrameTiming.{h,cpp}`, `AutomationProtocol.cpp`, the perf scenarios of #7.

### A11. A debug overlay drawn as raw quads, so it cannot perturb what it measures

- **Mechanism.** `crates/gpui/src/debug_overlay.rs` paints frame statistics as `Quad` primitives using a
  hand-rolled 5-by-7 bitmap font, merging horizontal runs of lit cells into single quads, "bypassing layout,
  text, and view invalidation entirely (to avoid infinitely triggering new frames)". Modes are `Hidden`,
  `Minimal` and `Full`; `Full` shows current, 1 %, 10 % and maximum over a 1000-sample ring.
- **Why it applies.** Any overlay built out of our own `<Text>` runs a paragraph layout per frame and invalidates
  the view that displays the number it just measured. For the 120 fps demo of #20 that is not a detail.
- **Lands in.** `packages/core/src/ScenePainter.cpp`, behind the automation channel of #214.

### A12. Fallback faces are chosen per grapheme cluster, before shaping, with a sticky slot

- **Mechanism.** `compute_run_spans` and `pick_covering_slot`
  (`crates/gpui_wgpu/src/cosmic_text_system.rs:885` and `:952`) iterate `grapheme_indices(true)` — so combining
  marks and emoji joiner sequences stay in one span — and choose, in order: primary for ASCII; primary if its
  charmap covers the character; then the **current** slot, sticky, "to avoid tearing clusters"; then the first
  fallback family that covers; and if nothing covers, deliberately `None` so the shaper's own script fallback
  takes over.
- **Why it applies.** #249 landed colour emoji and fontconfig fallback. The transferable idea is the *unit*: the
  grapheme cluster, not the codepoint, is what a fallback decision is made over, and the sticky slot is what
  stops a single family list from producing three runs where one would do. Zed #50073 and #5224 are the failures
  when the unit is wrong.
- **Lands in.** `packages/core/src/TextPipeline.cpp`.

### A13. Touchpad scroll locks to its dominant axis, and unlocks on a ratio

- **Mechanism.** `OngoingScroll::filter_at` (`crates/gpui/src/gestures.rs:64`). A gesture is delimited by touch
  phase where available and by a `SCROLL_EVENT_SEPARATION = 28 ms` timeout where not; the first non-zero delta
  picks the dominant axis; the lock releases only when the other axis exceeds `UNLOCK_LOWER_BOUND = 6 px` **and**
  is at least `UNLOCK_PERCENT = 1.9` times the locked one. While locked, the off-axis delta is zeroed.
- **Why it applies.** A two-finger touchpad scroll is never exactly axis-aligned. Without a lock, a vertical
  scroll in a horizontally scrollable container drifts sideways. #48 landed `axis_source`, `axis_stop` and
  `value120`; none of them is a lock.
- **Lands in.** `packages/core/src/InputPipeline.cpp`, `ScrollController.cpp`.

### A14. AccessKit is the upstream precedent ADR-0001 says does not exist

- **Mechanism.** GPUI models accessibility as a per-frame `accesskit::TreeUpdate` built during prepaint
  (`crates/gpui/src/window/a11y.rs`): a push and pop node stack, node identifiers derived from
  `GlobalElementId::accesskit_node_id()`, `Element::write_a11y_info` for properties,
  `Element::a11y_synthetic_children` for nodes with no element of their own (per-text-run nodes, caret
  positions), an `active_descendant` model for combo boxes and list boxes, and
  `note_focus_without_node(focus_id, reason)` which logs, once per focus change, that a focused element has no
  accessible node and needs an identifier and a role. The AT-SPI2 bridge itself is `accesskit_unix::Adapter`,
  wired in `crates/gpui_linux/src/linux/x11/window.rs:1956` — and **only** there: grep finds no accesskit in the
  Wayland or headless backends.
- **Why it applies.** ADR-0001's accepted risk says the AT-SPI mapping "has no upstream precedent to copy".
  AccessKit is one: a maintained Rust crate with an AT-SPI2 and D-Bus backend, a role and action vocabulary, and
  a tree-update protocol. That it is Rust does not disqualify the *model*, and it may not disqualify the library
  either. Zed's own X11-only wiring is the counter-evidence about how easy this is to leave half-done.
- **Lands in.** `docs/adr/` — this is a decision (E21), not an implementation.

### A15. Degrade explicitly, per protocol, and say so in the log

- **Mechanism.** `Globals::new` (`crates/gpui_linux/src/linux/wayland/client.rs:203`) binds every optional global
  as `Option<_>` and every mandatory one with a hard failure, with version ranges chosen for a reason:
  `wl_seat` is clamped to `5..=9` and **fails below 5** with the comment "We rely on the wl_pointer.frame
  event"; `wl_output` fails below 2; `wl_data_device_manager` is pinned to exactly version 3. Each missing
  optional global has a named consequence — no viewporter means `set_destination` is skipped, no decoration
  manager means client-side decorations, no cursor-shape manager means an Xcursor surface, no layer shell means
  `LayerShellNotSupportedError`.
- **Why it applies.** Our `bindGlobal` binds seven interfaces and the failure mode for a missing one is a
  segfault or a silently dead feature. A capability table with a stated degradation per entry is what makes
  "works on Hyprland, GNOME and KDE" a claim we can test.
- **Lands in.** `packages/core/src/WaylandWindow.cpp`, surfaced through the automation channel of #214.

## C. GPUI tests and rigs worth porting as test *shapes*

### C1. A seeded deterministic scheduler, with the failing seed printed for replay

`crates/scheduler/src/test_scheduler.rs` and `crates/gpui/src/platform/test/dispatcher.rs`. Configuration is
`TestSchedulerConfig { seed, randomize_order: true, allow_parking: false, capture_pending_traces, timeout_ticks:
0..=1000 }`. The properties, each of which is a design decision worth copying:

- The ready queue picks its next runnable from the seeded random source, so each seed is a different but
  reproducible interleaving.
- Parking is forbidden by default; blocking on real input or output fails. `dispatch_after` fails outright with
  "dispatch_after should not be called in tests. Use BackgroundExecutor::timer()" — real time is structurally
  unreachable.
- Timeouts resolve after a randomised *tick count*, not a duration, so a timeout-versus-completion race is
  seeded rather than wall-clock.
- `advance_clock_to_next_timer()` jumps the virtual clock instead of sleeping.
- `SEED` and `ITERATIONS` are environment variables; on failure the harness prints `failing seed: {seed}` and
  "You can rerun from this seed by setting the environmental variable SEED to {seed}".
- `simulate_random_delay()` (`scheduler.yield_random()`) lets production code declare its own interleaving points.
- `capture_pending_traces` (`PENDING_TRACES=1`) records backtraces of tasks still pending, to explain a hang.
- `#[gpui::test(iterations = N, seeds(a, b), retries = N, on_failure = "…")]` generates a plain `#[test]`, so
  the normal runner works unchanged; `#[gpui::property_test]` wraps property testing such that **one** `SEED`
  controls both case generation and interleaving, and it rejects a random-source parameter with a compile error.

Our #212 (threading-primitive conformance) and #77 (cross-thread contract stress) assert single interleavings.
This is the rig that makes them assert a *distribution* of interleavings and hand back a replayable seed.

### C2. Input simulation is one named call per platform event, with a stated return meaning

`crates/gpui/src/platform/test/window.rs` and `crates/gpui/src/app/visual_test_context.rs`:
`simulate_input(PlatformInput) -> bool` where the boolean means *the event was consumed*;
`simulate_resize`, `simulate_active_status_change`, `simulate_appearance_change`,
`simulate_scheduled_frame() -> bool` (consumes the scheduled-frame flag and returns false if nothing was
scheduled), `simulate_frame_request`, plus `frame_scheduled()` and `frame_wake_count()`. The waker deliberately
only increments a counter, "so tests can assert the wake protocol without coupling to frame timing". At the
context level: `simulate_keystrokes("cmd-shift-p b k s p enter")`, `simulate_input("abc")`,
`simulate_mouse_move`, `simulate_mouse_down`, `simulate_mouse_up`, `simulate_click`,
`simulate_modifiers_change`, `simulate_capslock_change`, `simulate_close() -> bool`. Every prompt is *queued* and
answered by `simulate_prompt_answer`, which fails with the full prompt text when nothing is pending.

  seeds; harness — a failing run prints the seed and the command to replay it, asserted by a meta-test;
  TSan-clean.

### E21. `feat(a11y): decide AccessKit for the AT-SPI bridge before hand-writing D-Bus` (#347)

- [zed#41138](https://github.com/zed-industries/zed/issues/41138) — open, +12, c12: the only substantial
  screen-reader issue in a four-year-old GPU-canvas editor, and it is about Windows. Linux AT-SPI is not filed at
  all, and GPUI wires `accesskit_unix::Adapter` only into its X11 backend
  (`crates/gpui_linux/src/linux/x11/window.rs:1956`) — grep finds no accesskit in the Wayland or headless
  backends.
- [zed#34591](https://github.com/zed-industries/zed/issues/34591) — closed: window focus on startup is `None` on
  both backends, so a keyboard-only user starts with focus nowhere.
- [zed#44854](https://github.com/zed-industries/zed/issues/44854) — open, c4: shortcuts still fire underneath a
  modal.

**Why it applies.** ADR-0001's accepted risk states that the AT-SPI mapping "has no upstream precedent to copy"
and that Flutter's direct-D-Bus proposal has been open and unfinished since November 2024. AccessKit is a
precedent: a maintained library with an AT-SPI2 backend, a role and action vocabulary, and a per-frame
tree-update protocol, used in production by at least one GPU canvas. The decision is not obvious — it is a Rust
crate, so adopting it means either a C ABI boundary or a second language in `packages/core`, against the
alternative of writing the `org.a11y.atspi` accessible, text, editable-text, value, selection and action
interfaces ourselves in C++. Nine issues in the M5 lane (#27, #61, #92, #264, #265, #266, #267) and one in M2
(#216) all assume an answer that has never been written down. It should be an ADR, and it should be written
before any of them starts.

- **Epic:** #177 (M5).
- **Status:** `status:blocked`, `needs:decision` — the decision is "AccessKit through a C boundary, or
  hand-written AT-SPI over D-Bus in C++", and it gates #27.
- **DEDUPE:** #27 owns the AT-SPI tree groundwork, #61 the role and name mapping, #92 announcements and caret
  events, #91 keyboard operability, #216 the serialized tree as an assertion surface, #264 to #267 the state,
  ordering, link and action interfaces. Every one of them presumes a transport; none names one.
- **Acceptance:** an ADR in `docs/adr/` recording the decision, the evidence (AccessKit's AT-SPI coverage against
  the interfaces #61, #264, #265, #266 and #267 need; the cost of a C boundary; Flutter's and Zed's records), and
  the consequences; #27's acceptance criteria amended to name the chosen transport; the model questions answered
  explicitly — whether the tree is rebuilt per frame or diffed, and how a node identity survives a Fabric view
  being recycled.

### E22. `test(renderer): an item that changes height inside the viewport must not move the line the user is reading` (#348)

- Rig and behaviour, from `crates/gpui/src/elements/list.rs`: `PendingScroll::{Absolute, Proportional}`,
  `ScrollAnchor`, and the tests `test_remeasure_item_preserves_scroll_offset`,
  `test_remeasure_then_scroll_does_not_revert_scroll_position`,
  `test_scroll_after_remeasure_clamps_to_shrunk_item_height`, `test_measure_all_after_width_change`.
- The React Native failures it corresponds to are already collected on #292 and #242; this is the third case
  neither of them covers.

**Why it applies.** #292 owns a prepend: content inserted *above* the anchor. #242 owns a programmatic scroll to
an index. Neither covers the most common case in a real list — an item already on screen changing height, because
an image finished decoding, a paragraph re-wrapped after a window resize, or a row expanded. A pixel offset
cannot express "keep this line where it is" across that change; an anchor of item plus offset into item can, and
GPUI's second variant — a *proportional* anchor for when the whole list is being resized and every item scales —
is the answer to the window-resize case specifically.

- **Epic:** #173 (M1).
- **DEDUPE:** #292 owns `maintainVisibleContentPosition` on a prepend in the mounting transaction; #242 owns
  `scrollToIndex` landing; #45 (closed) owns the `onScroll` cadence; #109 (closed) owns programmatic scroll not
  feeding itself; #46 (closed) owns first-frame content size. None covers a remeasure of a visible item.
- **Acceptance:** unit (100 % gate) — the anchor arithmetic: an item above the anchor grows or shrinks, the
  anchor item itself grows or shrinks under both anchor modes, the anchor item shrinks below the current offset
  (clamped), and the anchor item is removed; e2e — a 200-row list scrolled to the middle, with row 40 doubling in
  height, keeps the row at the viewport top at the same pixel offset; e2e — a window resize with a proportional
  anchor keeps the same fractional position; golden — the viewport before and after an in-view image finishes
  decoding.

### E23. `test(harness): the golden and e2e rigs run under more than one compositor` (#349)

- [zed#44814](https://github.com/zed-industries/zed/issues/44814) — closed, +13 and
  [zed#50574](https://github.com/zed-industries/zed/issues/50574) — closed, c18: a rendering freeze under niri.
- [zed#55345](https://github.com/zed-industries/zed/issues/55345) — closed, +2, c7: a freeze on Hyprland when
  fullscreen and opening popups. [zed#24139](https://github.com/zed-industries/zed/issues/24139) — closed, c8: a
  crash on sway when the window loses focus. [zed#19254](https://github.com/zed-industries/zed/issues/19254) —
  closed, **c19**: a crash while resizing under KDE.
- [zed#23610](https://github.com/zed-industries/zed/issues/23610) — closed and
  [zed#36303](https://github.com/zed-industries/zed/issues/36303) — closed, +3: the same build behaves
  differently under GNOME, KDE, X11 and Wayland.
- [zed#56314](https://github.com/zed-industries/zed/issues/56314) — closed: GPUI's own examples do not run under
  Wayland.

**Why it applies.** Our golden and e2e rigs run under `weston --backend=headless` and `cage`. Every failure above
is a *compositor-specific* behaviour: which globals are advertised (Mutter has no decoration manager, KWin has a
blur manager), whether frame callbacks arrive for an unfocused surface, how aggressively configures are sent, and
what a protocol error is answered with. E3, E5, E6 and E11 each assert behaviour that only one of those
compositors exercises, and asserting them against one implementation proves the implementation, not the
protocol. A second and third headless compositor in the matrix is cheap — they are packages, pinned by digest
like the existing ones — and it is the only way "works on Hyprland, GNOME and KDE" becomes a claim with a test
behind it.

- **Epic:** #209 (test-suite parity).
- **DEDUPE:** #6 (closed) owns the lavapipe plus headless-compositor rig, #33 (closed) the first window golden,
  #7 the e2e driver and its virtual input, #304 a flake under cage. All of them assume one compositor; none
  parameterises over compositors.
- **Acceptance:** harness — the compositor is a parameter of the golden and e2e runners, with at least two
  implementations pinned by digest (`weston --backend=headless` and a wlroots-based one) and the matrix
  documented in the harness README; harness — a scenario declares which compositor capabilities it needs and is
  skipped, loudly and by name, where they are absent; CI — the full e2e suite runs on both, and a
  compositor-specific failure names the compositor in the artifact; harness unit tests (Vitest, 100 %) for the
  capability declaration and the skip logic.

## F. The ten highest-value picks

1. **#347 — decide AccessKit for AT-SPI (E21).** It is the only entry that changes the shape of a whole
   milestone, it gates nine open issues, and ADR-0001's claim that no precedent exists is now false.
2. **#327 — a policy for every `VkResult` (E1).** We handle one error out of seven. A lid close currently kills
   the application, and zed#23288 has been open for a year with 28 reactions because retrofitting it is hard.
3. **#329 — decorations, the drawn titlebar and the application identifier (E3).** Under GNOME the window has no
   chrome at all, and zed#14165's 126 reactions are what that costs. It is also the first thing any screenshot of
   the flagship shows.
4. **#330 — the serial ledger (E4).** Five upcoming pieces of work need it, it is fifty lines, and getting it
   wrong is zed#58651: breaking copy and paste for the user's entire desktop.
5. **#340 — the text-input session follows focus (E14).** #26 landed the composition; this is everything that
   makes it survive a focus change, a window switch or a suspend, which is the entire fcitx5 and ibus bug mass.
6. **#346 — the seeded deterministic scheduler (E20).** It is a rig, so it multiplies every threading assertion
   we already have and every one #209 will add, and it turns a one-in-a-thousand interleaving from a flake into
   a replayable seed.

   Vulkan — is the configuration our entire golden suite depends on, and the failure is silent.

   "broken pipe", and we will spend the debugging time twice.
10. **#342 — the paragraph cache and the layout mutex (E16).** Two unmeasured risks in one function on the
    hottest path we have, with a known-good 40-line shape to copy and no eviction policy to design.
