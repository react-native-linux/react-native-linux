# Electron on desktop Linux, mined — 2026-09-07

- Research report, 2026-09-07. Corpus: `electron/electron` at `5c0ffc5` (shallow, blob-filtered clone,
  2026-09-07) plus its issue tracker, plus Chromium's Ozone/Wayland platform read through raw URLs at
  `chromium/chromium@main`. Reaction (`+n`) and comment (`cN`) counts are the API values on that date.
- **Where Electron does NOT overlap with us, stated first so the rest is readable.** Electron is a web engine.
  Blink owns layout, text shaping, line breaking, the DOM, the CSS cascade, scroll physics, hit testing, the
  accessibility tree, the compositor's layerisation and its damage model. **None of that is transferable**: our
  equivalent of Blink is Fabric plus SkParagraph plus our own scene, and copying Chromium's answers there would
  be copying a browser into a React Native platform. Equally out of scope: the multi-process architecture, the
  sandbox, V8 and Node integration, the extension system, `webContents`, `<webview>`, service workers, protocol
  handlers, PDF, media capture, WebRTC and the auto-updater. Electron's own Linux-specific
  differentiators — the tray, global shortcuts, application menus, native dialogs, notifications, screen
  capture — are desktop-shell integrations React Native has no API for and that ADR-0001 does not commit us to;
  where a *lesson* from one of them generalises it is recorded here, but none of them is proposed as work.
- **What does overlap, and why this corpus is worth reading.** Electron is the only widely shipped application
  platform that draws its entire interface itself onto a Wayland surface, on Vulkan-or-GL, with client-side
  decorations it renders, and then has to be a good Linux desktop citizen anyway. Strip Blink out and what
  remains — `shell/browser/native_window_views.cc`, `shell/browser/ui/views/electron_frame_view_linux.cc`,
  `shell/browser/ui/electron_desktop_window_tree_host_linux.cc`,
  `shell/browser/ui/views/freedesktop_nav_button_provider.cc`, `shell/common/platform_util_linux.cc`, and the
  Ozone/Wayland client under `ui/ozone/platform/wayland/host/` — is *exactly* the surface ADR-0001 makes ours:
  toplevel identity, decorations, insets, scale, cursor, text input, clipboard, activation, GPU fallback, and a
  test rig that has to prove any of it under a headless compositor. Like the Zed pass, this is a **failure-mode
  oracle**, not a parity oracle.
- **The single most important structural difference, and it is load-bearing for section E.** Chromium survives a
  lost GPU as a *process* event: the GPU process dies, the browser process notices, walks a fallback ladder
  (`HARDWARE_VULKAN` → `HARDWARE_GL` → `SOFTWARE_GL` → `DISPLAY_COMPOSITOR`) and restarts. We are one process.
  Every recovery Electron gets for free is, for us, either an in-process recovery we write (#327) or a crash.
  E4 makes that a decision rather than an omission.
- **Dedupe.** Every candidate was grepped against the title and body of all open and closed issues in this
  repository (`gh issue list --state all --limit 700`), and the bodies of #40, #51, #70, #83, #87, #218, #249,
  #294, #326, #327, #328, #329, #330, #334, #336, #337, #340, #345 and #349 were read in full. The twenty-three
  Zed-derived issues #327–#349 were treated as already owning their subject: section D names each one that
  swallowed a candidate. Every section E entry carries a `DEDUPE` line.
- **Result:** 14 sub-issues proposed and filed (section E), 21 candidates dropped (section D).

## A. What Electron does that we can copy as an approach

Each entry: the mechanism and where it lives, why it applies to a Skia/Wayland canvas, and where it lands in our
tree.

### A1. Non-capability is documented per API, in the API reference, with the value the call returns

- **Mechanism.** Electron's `docs/api/*.md` annotate Wayland limits inline, at the method: `base-window.md:785`
  — "On Wayland, this method will return `{ x: 0, y: 0, ... }` as introspecting or programmatically changing the
  global window coordinates is prohibited"; `:1005` — `getPosition()` returns `[0, 0]`; `:212` — "On Wayland,
  'minimized' is not currently a supported state. The minimize event will only fire when triggered by
  client-side decoration"; `screen.md:113`, `:148`, `:160` — `getCursorScreenPoint` "will return the point
  passed". `browser-window.md` carries eleven separate "Not supported on Wayland (Linux)" notes and four "may
  not work as some window managers restrict programmatic window resizing". `global-shortcut.md` goes further and
  documents the *behavioural* consequences of the portal path: GNOME shows a consent dialog, KDE binds silently,
  bindings persist keyed by portal identity, and an unresolvable desktop identifier makes GNOME deny every bind
  "silently, from the app's perspective".
- **Why it applies.** React Native's JavaScript surface is written against iOS and Android, where every one of
  these has an answer. `Dimensions.get('screen')`, window position, "is the app minimised", a synchronous cursor
  position — an out-of-tree platform either implements them, refuses them, or lies. Electron's discipline is the
  third option made honest: refuse in writing, at the method, with the exact value returned.
- **Lands in.** The support matrix of #87, and a per-API table in `docs/`, driven by E5.

### A2. The application identity is one string, set on three protocols, and derived from the desktop file

- **Mechanism.** `NativeWindowViews::NativeWindowViews` (`shell/browser/native_window_views.cc:321-333`):
  `GetXdgAppId()` is read once and used for `params.wm_class_name` (lower-cased), `params.wm_class_class` and
  `params.wayland_app_id`, with the comment "Set the WM_CLASS and XDG App ID to the same value for best
  compatibility with both X11 and Wayland". `GetXdgAppId()` itself
  (`shell/common/platform_util_linux.cc:463-478`) reads the `CHROME_DESKTOP` environment variable and strips a
  `.desktop` suffix — that is, the identity comes from the *installed desktop entry*, not from a constant in the
  binary. The same identity is what `launcher_entry.cc` sends to `com.canonical.Unity.LauncherEntry` as
  `application://<desktop-id>` for progress and badge counts, and what the `GlobalShortcuts` portal binds
  against.
- **Why it applies.** #329 owns `xdg_toplevel.set_app_id`. What Electron adds is that the application identifier
  is not a window property, it is *the application's identity across the whole desktop*: icon lookup, window
  grouping, window rules, taskbar association, portal permission storage and notification attribution all key on
  it, and it must equal the basename of a `.desktop` file our CLI actually installs. That coupling is a CLI and
  packaging obligation, and it is E1.
- **Lands in.** `packages/core/src/WaylandWindow.cpp`, `packages/cli` (the init template's desktop entry).

### A3. The client-side decoration inset is inflated back out of every size constraint, exactly once

- **Mechanism.** `ElectronDesktopWindowTreeHostLinux::GetMinimumSizeForWindow` and `GetMaximumSizeForWindow`
  (`shell/browser/ui/electron_desktop_window_tree_host_linux.cc:101-127`) take the application's logical
  constraint and `Enlarge` it by `GetRestoredFrameBorderInsets()`, with the comment: "Electron treats min/max
  constraints as the logical window size, but Chromium expects widget bounds including CSD insets … So we
  inflate constraints by insets to avoid double subtraction. This is still OK for SSD frames or X11 where the
  insets are 0." `CalculateInsetsInDIP` returns zero insets whenever the frame is not shown, so the same
  arithmetic covers server-side decorations and the frameless case without a branch at every call site. A
  maximum of `0` is deliberately *not* inflated, because zero means "no constraint".
- **Why it applies.** The moment we draw our own titlebar and shadow gutter, the surface is larger than the
  application's view of the window, and there are at least five consumers of "the size": Yoga's root node,
  `Dimensions`, `useWindowDimensions`, the swapchain, and hit testing. Every one of them must be on the same
  side of the inset, and Electron's tracker shows what happens otherwise — #50017 "Window size off by one" (c8),
  #51679 (+5, c12) and #45916 (c14).
- **Lands in.** `packages/core/src/WaylandWindow.{h,cpp}`, `ToplevelState.h`, `DimensionsSource.cpp`; E9.

### A4. Tiled edges are read, but GNOME's tiled edges are not trusted

- **Mechanism.** `OnWindowTiledStateChanged`
  (`shell/browser/ui/electron_desktop_window_tree_host_linux.cc:151-165`) collapses the four
  `ui::WindowTiledEdges` booleans into one: "GNOME on Ubuntu reports all edges as tiled even if the window is
  only half-tiled, so do not trust individual edge values." The result is `tiled && !maximized`, which then
  drives whether the drawn frame keeps its shadow gutter and rounded corners at all.
- **Why it applies.** GPUI's `inset_by_tiling` drops the gutter per edge; Electron says per-edge information is
  not reliable on the desktop with the largest installed base. Since we draw the gutter, the rounded corners and
  the resize handles ourselves, "am I tiled" changes our painted geometry *and* our non-client hit regions, and
  the safe reading of that bit is a compositor-specific quirk worth inheriting rather than rediscovering.
- **Lands in.** `packages/core/src/WaylandWindow.cpp`, `ScenePainter.cpp`; an acceptance point of E9.

### A5. The opaque region is set explicitly, and only when the surface is actually opaque

- **Mechanism.** `UpdateFrameHints`
  (`shell/browser/ui/electron_desktop_window_tree_host_linux.cc:219-245`). When no drawn shadow is wanted, the
  input region is cleared and — only if `ui::OzonePlatform::GetInstance()->IsWindowCompositingSupported()` — the
  opaque region is set either to the empty vector (translucent, or opacity below 1) or to
  `ScaleToEnclosingRect(gfx::Rect(size), device_scale_factor())`, that is, **the region is computed in device
  pixels from the logical size and the current scale, on every bounds change and every state change**. When a
  shadow *is* drawn, the base class computes the region from the frame's own geometry, and a non-opaque window
  overrides it back to empty.
- **Why it applies.** A wrong opaque region is invisible on our own machine and expensive on someone else's: the
  compositor either blends a surface it could have scanned out, or treats a translucent surface as opaque and
  renders garbage behind our rounded corners. GPUI's answer was to give up on the region under client-side
  decorations; Electron's is to keep it and recompute it with the scale, which is the answer we need for #338's
  damage work to be worth anything.
- **Lands in.** `packages/core/src/WaylandWindow.cpp`, next to `wl_surface.damage_buffer` (#338).

### A6. The drawn titlebar's glyphs come from the desktop's own symbolic icon theme

- **Mechanism.** `freedesktop_nav_button_provider.cc` renders the window controls itself and takes only the
  glyphs from the system: `kIconNames = {"window-minimize-symbolic", "window-maximize-symbolic",
  "window-restore-symbolic", "window-close-symbolic"}`, loaded through
  `gtk_icon_theme_lookup_icon_for_scale(..., icon_size, scale, GTK_ICON_LOOKUP_USE_BUILTIN |
  GTK_ICON_LOOKUP_GENERIC_FALLBACK)` and recoloured via `gtk_icon_info_load_symbolic`
  (`shell/browser/ui/gtk/gtk_symbolic_icon_provider.cc`) — note the **scale is a lookup parameter**, not a
  post-scale. The surrounding chrome is a per-desktop style chosen by theme name (`DetectButtonStyle`, line
  121): an Adwaita style whose numbers are libadwaita's (24 px circle, foreground at 10/15/30 % opacity, 5 px
  margin, 3 px inter-spacing) and a Breeze style (18 px circle, glyph only at rest, the palette's negative
  colour for close). The provider returns `nullptr` when GTK3 is not loadable, and the caller falls back to
  Chromium's own vector caption buttons. One more detail worth stealing: caption buttons get
  `SetAnimationDuration(zero)`, because the hover cross-fade "rasterizes at the nearest integer scale, which
  momentarily shifts/blurs the glyph on fractional-scale displays".
- **Why it applies.** #329 commits us to drawing a titlebar under GNOME. This is what "drawn, but native
  looking" costs and how far a canvas toolkit can get without a widget toolkit: theme-sourced monochrome glyphs
  plus about eighty lines of per-desktop geometry constants.
- **Lands in.** `packages/core/src/ScenePainter.cpp` and the titlebar work of #329, as an amendment.

### A7. GPU failure is a ladder with a crash counter, not a boolean

- **Mechanism.** Chromium's `content/browser/gpu/gpu_data_manager_impl_private.cc` builds `fallback_modes_` at
  startup — `DISPLAY_COMPOSITOR` first (the bottom of the stack), then `SOFTWARE_GL`, then the hardware modes
  pushed on top in preference order (`HARDWARE_GL`, `HARDWARE_GRAPHITE`, `HARDWARE_VULKAN`) — and
  `FallBackToNextGpuMode()` pops one each time the current mode fails. Modes the GPU process has *reported*
  unsupported are erased from the list (`std::erase_if(fallback_modes_, …)`, line 1130) so a later fallback
  cannot re-select them. Electron exposes the bottom of that ladder to the application as
  `app.disableHardwareAcceleration()`, which appends `--disable-gpu` to the command line explicitly "so that all
  Chromium subsystems … see the decision" and also calls `GpuDataManager::DisableHardwareAcceleration()` if the
  manager is already initialised (`shell/browser/api/electron_api_app.cc:1158-1200`).
- **Why it applies.** ADR-0001 accepts Vulkan driver bugs "for which we have no workaround" as a risk and stops
  there. Electron #32317 (+22, c42) and #51941 (c6) are what the risk looks like when it arrives: a permanently
  broken installation with a message the user cannot act on. The transferable parts are the ordered ladder, the
  rule that a failed mode is *removed* rather than retried, and a single documented escape hatch that is set
  before any subsystem reads it.
- **Lands in.** `packages/core/src/SkiaVulkanRenderer.cpp`, `RendererSelection.{h,cpp}`; E3.

### A8. The `done` serial gates what a text input applies

- **Mechanism.** `ui/ozone/platform/wayland/host/zwp_text_input_v3.cc`. The client keeps three copies of the
  input-method state — `pending_ime_data_`, `applied_input_events_`, `committed_ime_data_` — and
  `IsImeStateConsistent()` is literally
  `committed_ime_data_.commit_count == applied_input_events_.last_done_serial` (line 213).
  `zwp_text_input_v3` sends `preedit_string`, `commit_string` and `delete_surrounding_text` as *pending* state
  that only `done` applies, and `done` carries the serial of the `commit` it answers; anything answering an
  older serial describes a state the application has already left. `Reset()` clears the surrounding text as well
  as the preedit — with a source comment explaining that although Chromium only expects the preedit to be reset,
  the compositor stops sending surrounding-text updates after an internal cancel (crbug.com/353915732).
  `Enable()` resets all four state objects, so a re-enable can never inherit the previous field's state.
- **Why it applies.** #26 landed our composition and #340 owns the session lifecycle. Neither states the serial
  rule, and without it every fcitx5 and ibus bug in the Zed corpus is reachable again through a different door:
  events for a composition the user has already abandoned get applied to the field they moved to.
- **Lands in.** `packages/core/src/TextInputClient.{h,cpp}`; E6.

### A9. The startup activation token is extracted from both the command line and the environment, and re-injected

- **Mechanism.** `base::nix::ExtractXdgActivationTokenFromEnv` at `shell/app/electron_main_delegate.cc:365`,
  `base::nix::ExtractXdgActivationTokenFromCmdLine` at `shell/browser/api/electron_api_app.cc:448` — both,
  because a second instance is handed its token on the command line while a first instance finds it in
  `XDG_ACTIVATION_TOKEN`/`DESKTOP_STARTUP_ID`. It is then re-injected around the activation path with
  `base::nix::ScopedXdgActivationTokenInjector` (`electron_api_app.cc:1092`), passed to the OpenURI portal as
  the `activation_token` option (`platform_util_linux.cc:192-213`), and *received back* from libnotify:
  `notify_notification_get_activation_token` is looked up with `dlsym` and its result handed to
  `base::nix::SetActivationToken` (`shell/browser/notifications/linux/libnotify_notification.cc:56-227`), so a
  click on a notification carries the focus permission with it.
- **Why it applies.** #336 owns consuming the startup token. The generalisation is that an activation token is a
  *transferable focus permission* with three sources and three sinks, and the second-instance case — the one the
  flagship will hit, because a desktop application is launched twice — needs the command-line source. E12.
- **Lands in.** `packages/core/src/WaylandActivation.{h,cpp}`, `packages/virtual-modules` (`Linking`).

### A10. The test rig names, in a reviewed file, which tests cannot run under Wayland

- **Mechanism.** Three separate, explicit lists. (1) `script/wayland-test-allowlist.txt` — the *entire* set of
  spec files run in the Wayland CI job, six of about ninety: `parse-features-string`, `types`, `version-bump`,
  `api-app`, `api-browser-window`, `api-clipboard`. (2) `isWayland` in `spec/lib/spec-helpers.ts` — a predicate
  over `XDG_SESSION_TYPE`, `WAYLAND_DISPLAY` and `--ozone-platform=wayland` — used as `ifdescribe(!isWayland)`
  on `focus and blur`, `setAlwaysOnTop`, `moveTop`, `setContentBounds`, `visibleOnAllWorkspaces` and
  `disabling parent windows`: the six behaviours Wayland refuses to give a client. (3)
  `spec/disabled-tests.json`, a flat array of full test titles with a comment as its first element.
- **Why it applies.** This is the honest form of the thing we will otherwise do implicitly. Our rig is a
  headless compositor plus software Vulkan by design (#33, #6, #349), so "this cannot be asserted here" will
  arise, and the choice is between a named predicate in a reviewed file and a slowly rotting set of quiet skips.
- **Lands in.** `packages/test-harness/`; E14.

### A11. The headless Wayland rig is twenty lines of shell, and it waits for the socket

- **Mechanism.** `script/actions/run-tests-wayland.sh`: export `XDG_SESSION_TYPE=wayland` and
  `WAYLAND_DISPLAY=wayland-99`; create `XDG_RUNTIME_DIR` with `mktemp -d` and `chmod 700` if unset, with a
  `trap` that kills weston and removes it; start
  `weston --backend=headless-backend.so --socket=$WAYLAND_DISPLAY --idle-time=0`; then **poll for the socket to
  exist**, up to a hundred times at 100 ms, before starting the application with `--ozone-platform=wayland`.
  `--idle-time=0` is the detail that matters: a headless compositor that idles stops sending frame callbacks and
  every timing assertion in the suite becomes a flake.
- **Why it applies.** #33 already runs lavapipe plus headless weston. `--idle-time=0`, the socket wait instead
  of a sleep, and the private `XDG_RUNTIME_DIR` per run are three concrete hardening steps for it.
- **Lands in.** `packages/test-harness/`, the compositor launcher of #33 and #349.

### A12. A pixel assertion polls until the pixel appears, and its failure is an uploaded artifact

- **Mechanism.** `spec/lib/screen-helpers.ts`. `ScreenCapture.forWindow(window)` captures **one window's own
  composited contents** rather than the display, with a doc comment explaining why: another test's window or "a
  stray system dialog left behind by an earlier test on CI" cannot then affect the result.
  `expectColorAtPointMatches` loops `captureFrame` until the colour matches or `TIMEOUT = 3000` expires, keeping
  the last frame it managed to capture so the failure artifact is never empty; on failure it resizes to 720 px
  wide on CI, uploads it through `createArtifactWithRandomId`, and puts the point, the target description, the
  expected and the actual colour in the assertion message. Colours are compared by Euclidean distance with a
  threshold, not by equality. `PAUSE_CAPTURE_TESTS` inserts a one-second pause for a human watching.
- **Why it applies.** The window-scoped capture is the transferable idea, and so is the failing-artifact
  discipline. The polling is **not**: our goldens settle deterministically (#296, #301), and a three-second poll
  would trade a real assertion for a slow one. Recorded here so the distinction is deliberate.
- **Lands in.** #234's per-element crops, as a note; otherwise dropped (D19).

### A13. Cleanup is asserted, not hoped for

- **Mechanism.** `spec/lib/window-helpers.ts`. `closeWindow` awaits the `closed` event when the window still has
  live contents, "as it may have `<webview>` children which need to be destroyed first"; `assertNotWindows` then
  schedules an assertion on the *next tick* that `BaseWindow.getAllWindows()` is empty, and in its `finally`
  destroys whatever leaked so the next test still starts clean. `cleanupWebContents` counts what it destroyed
  and returns the count.
- **Why it applies.** #76 (teardown and reload leak gate) and #247 (a node unmounts while hovered) both need
  exactly this shape: destroy, await the completion event rather than a tick, then assert the registry is empty
  and repair it so one leak does not cascade into fifty failures.
- **Lands in.** `packages/test-harness/`, the scenario teardown of #7.

### A14. CI takes a screenshot when the run times out

- **Mechanism.** `.github/workflows/pipeline-segment-electron-test.yml:430` — a step that runs on timeout or
  cancellation and writes `spec/artifacts/screenshot-timeout-<timestamp>.png` from the whole display. The Linux
  test job also runs with `--enableRerun=3` (lines 411-413), and the Wayland job is pinned to a single shard.
- **Why it applies.** A hung e2e scenario under a headless compositor currently tells us nothing. One screenshot
  of the compositor at the moment of the timeout is the cheapest possible answer to "was it a blank window, a
  modal, or a stuck first frame". The `--enableRerun=3` half is the anti-pattern: it is what a suite does
  instead of fixing #304.
- **Lands in.** `.github/workflows/`, alongside the e2e job of #7.

### A15. The portal is preferred, the legacy path is the fallback, and which one is in use is a state

- **Mechanism.** `ShowItemHelper` in `shell/common/platform_util_linux.cc:58-284`: an
  `enum class ApiType { kNone, kPortal, kFileManager }` resolved by an actual name-owner check on
  `org.freedesktop.portal.Desktop` before either path is used, with "The portal API is always preferred if
  available" stated in the code, and a defined behaviour when neither exists. The request itself is a
  `dbus_xdg::Request` with a reply handler, not a fire-and-forget signal.
- **Why it applies.** Every desktop integration we will add — colour scheme (#326), file dialogs, opening a URL
  (#23) — has this exact shape: a portal, a legacy path, and a real possibility that neither is present.
  Resolving it to a tri-state once, rather than testing for the portal at each call site, is what keeps the
  degradation testable.
- **Lands in.** `packages/core/src/PortalClient.{h,cpp}`, consumed by the modules of #23 and #326; E13.

## C. Electron test shapes worth porting

### C1. The Wayland job is a named allowlist, and the skips are a predicate

See A10. Three files, three purposes: `script/wayland-test-allowlist.txt` says which suites the Wayland job runs
at all, `isWayland` in `spec/lib/spec-helpers.ts` says which individual behaviours cannot be asserted under
Wayland *anywhere*, and `spec/disabled-tests.json` is the quarantine list. The second one is the interesting
one, because the six suites it guards — focus and blur, always-on-top, `moveTop`, `setContentBounds`,
`visibleOnAllWorkspaces`, disabling parent windows — are a precise, executable statement of what Wayland
withholds from a client. Ours would guard window position, window raise, the minimised state, and global pointer
position. E14.

### C2. A window-scoped capture, not a display capture

`ScreenCapture.forWindow` (A12) captures one window's composited output through the desktop capturer, and the
doc comment states the rule: only a test that verifies how our window composites *over* another window needs the
whole display. Our golden rig captures the surface; the transferable idea is that the *display* capture is a
distinct and rarer assertion, needed exactly once — for a transparent window — and that mixing the two is how a
suite gets flaky on a shared CI machine.

### C3. The failure of a visual assertion is an uploaded artifact with the point named

Also A12: the last successfully captured frame is retained even when the final capture fails, resized on CI, and
uploaded; the message carries the coordinate, the target, the expected and the actual colour. #6 already writes
a diff image; the transferable detail is retaining the *last* frame rather than the *current* one, so a timeout
still produces an image.

### C4. Teardown asserts the registry is empty and then repairs it

`closeWindow(..., { assertNotWindows: true })` (A13): await the real completion event, assert on the next tick
that no windows remain, and destroy any that do inside the `finally`. One leaked window then fails one test
instead of every subsequent one. Directly applicable to #7's scenario teardown and #76's leak gate.

### C5. `--idle-time=0`, and wait for the socket rather than sleeping

A11. Both are one-line hardening of the compositor launcher #33 and #349 already need, and both are the kind of
thing that is otherwise discovered through a week of intermittent CI failures.

### C6. A screenshot on timeout is a CI step, not a test feature

A14. It costs one workflow step and answers the only question a hung headless e2e run raises.

### C7. A tracking issue that audits documentation against the suite

[electron#53239](https://github.com/electron/electron/issues/53239) — "Tracking: documented APIs without spec
test coverage (docs/api vs spec audit)". The shape worth copying is not the issue but the *gate*: the documented
surface and the tested surface are two lists, and their difference should be computed by CI rather than by a
person periodically. #69 does this for component props; nothing does it for module methods. E11.

### C8. What Electron does not test, which is the warning

The Wayland job runs **six spec files of about ninety**, on one shard, with `--enableRerun=3`. `ScreenCapture`
carries the comment "NOT yet supported on Linux in CI due to empty sources list" — that is, **no visual
assertion runs on Linux at all**, on either display server. `drag-region-spec.ts` depends on `robotjs` inside a
`try` block. The consequence is section B2: an inset arithmetic defect that reaches users as "window size off by
one", a resize gutter that eats clicks, and a drag region that swallows its own double click — three defects
that a single non-client hit-test unit test would have caught, in a project that has neither the unit test nor a
Linux visual suite to catch it later. Our 100 % gate plus lavapipe goldens exist precisely so this section stays
short.

### E1. `feat(cli): the application identity is one string — app_id, the desktop entry it names, and the icon both of them resolve` (#366)

### E3. `feat(core): a renderer fallback ladder with a crash counter — software raster is a tier, the failed tier is never retried, and the choice is reported` (#368)

- [electron#32317](https://github.com/electron/electron/issues/32317) — open, **+22, c42**: "GPU crashed in all
  recent Versions: Passthrough is not supported, GL is disabled" — the ladder at the bottom, with no message a
  user can act on. [electron#51941](https://github.com/electron/electron/issues/51941) — open, c6: "Electron app
  is just a grey screen".
- Mechanism: `content/browser/gpu/gpu_data_manager_impl_private.cc` — `fallback_modes_` built bottom-up
  (`DISPLAY_COMPOSITOR`, `SOFTWARE_GL`, then the hardware modes), `FallBackToNextGpuMode()` popping one per
  failure, and `std::erase_if(fallback_modes_, …)` (line 1130) removing any mode the GPU process reported
  unsupported so it cannot be re-selected. Electron's escape hatch is `App::DisableHardwareAcceleration`
  (`electron_api_app.cc:1158-1200`), which appends `--disable-gpu` before any subsystem reads it.

**Why it applies.** ADR-0001 accepts "driver bugs for which we have no workaround" and stops. #334 will tell a
user *which* feature is missing; #327 will recover from a `VkResult`. Neither says what the application does on
the third consecutive failed initialisation, and the honest answer on Linux is not "exit": it is a named lower
tier — lavapipe, which our own CI already proves renders correct pixels — plus a persisted decision so the next
launch does not repeat the crash, plus one documented override for when we choose wrong.

- **Epic:** #174 (M2).
- **DEDUPE:** #334 owns the preflight and the named missing feature; #327 owns per-`VkResult` recovery once a
  device exists; #333 owns *which* adapter is picked among working ones; #328 owns the invisible-window class;

  crash counter, the persistence, or the user-facing override. #369 may change where this lives.
- **Acceptance:** unit (C++, 100 % gate) — the ladder as a pure function over (available adapters, reported
  failures, consecutive crash count, override) returning the next tier, including "every tier exhausted" and
  "the failed tier is removed, not retried"; unit — the persisted decision round-trips and is invalidated when
  the adapter set changes; e2e — with the hardware tier forced to fail, the harness still renders the reference
  frame on the software tier and the automation channel reports the tier and the reason.

### E4. `docs: decide the process model for renderer faults — Chromium survives a lost GPU because it is a separate process, and we are not` (#369)

- Every entry in section B5 marked Electron/Chromium-specific exists because the GPU lives in another process:
  the browser process observes the crash, walks the ladder of E3, and repaints. Our equivalent of that crash is
  an abort inside the application's only process, taking the JavaScript state with it.
- [zed#62621](https://github.com/zed-industries/zed/issues/62621) — open, from the previous pass: an illegal
  shader opcode triggers an amdgpu MODE2 reset and takes the whole Wayland session down. That is the far end of
  the same axis, from a single-process GPU canvas.

**Why it applies.** #327 (recover from `VkResult`), #334 (preflight) and E3 (the ladder) are all in-process
mitigations, and each of them assumes the process is still alive to run it. A device loss caused by a driver
defect is not always an error code; it can be a fatal signal raised inside the driver, on our render thread. The
decision this issue closes is: do we accept that a driver fault is a process fault, or does the renderer get an
isolation boundary — and if it does, what does that cost a 120 fps target ADR-0001 states in terms of a single
compositor deadline. It must be written *before* E3 is implemented, because "restart the render tier" and
"restart the render process" are different implementations of the same sentence.

- **Epic:** #174 (M2). Filed `status:blocked` with `needs:decision`.
- **DEDUPE:** #327, #331, #334 and E3 are all mitigations inside one process; ADR-0001 discusses the JS, commit
  and render *threads* and never discusses process boundaries; #78 owns build cost, not runtime topology; #345
  owns frame latency measurement. Nothing in the tracker contains "process model".
- **Acceptance:** an ADR in `docs/adr/` recording the decision, the cited or measured cost of the rejected
  option, and the failure classes each option covers; if the answer is single-process, the ADR states what a
  fatal driver signal does and what the user sees, and E3's acceptance is amended to match; if it is not, a
  follow-up issue owns the boundary, its threading contract and its measured frame cost. No code lands under
  this issue.

### E6. `fix(text): the zwp_text_input_v3 done serial gates what is applied — preedit and commit answering a stale serial are discarded` (#371)

- Mechanism: `ui/ozone/platform/wayland/host/zwp_text_input_v3.cc`. Three state objects — `pending_ime_data_`,

### E12. `feat(core): a second instance hands its arguments and its activation token to the first, which requests attention rather than assuming it` (#377)

## F. The ten highest-value picks

1. **#369 — decide the process model for renderer faults (E4).** It is the only entry that can change the shape
   of the renderer, it gates how E3 and #327 are implemented rather than merely how they are tested, and
   ADR-0001 discusses three threads without ever discussing a process boundary. Every entry in section B5 marked
   Electron/Chromium-specific is a failure we inherit in full because we made the opposite choice implicitly.
2. **#374 — the decoration inset applied exactly once (E9).** Five consumers read the window size, #329 is about
   to make the surface bigger than the window, and Electron has three separate open bugs from exactly this. It
   is also the cheapest of the ten: one conversion pair and a table.
3. **#368 — the fallback ladder with a crash counter (E3).** electron#32317 is +22 and c42 of users with a
   permanently broken installation and no message they can act on. We already run lavapipe in CI, so the lower
   tier exists; what is missing is the decision to treat it as a product tier and never retry a failed one.
4. **#371 — the text-input `done` serial (E6).** #26 landed the composition and #340 will make it survive focus
   changes; without the serial rule a slow input method applies an abandoned composition to whichever field is
   focused now, and Chromium's own implementation carries a crbug link explaining why the naive reading is
   wrong.
5. **#367 — the non-client hit region (E2).** The first thing a user does with a drawn titlebar is drag it, and
   Electron has one open bug for a gutter that is too greedy and another for a drag region that is too greedy.
   Both are unit-testable before any compositor is involved.
6. **#373 — ready is the first presented frame (E8).** Three consumers need it — the application, the harness
   and our own state machine — and the harness one removes a class of timeout flakes before we have written
   them.
7. **#372 — the default font family (E7).** Every `<Text>` without an explicit family goes through the least
   specified code path in the text stack, and electron#53499 is what wrong looks like: an entire interface in

8. **#366 — one application identity (E1).** The icon, the window rules, the taskbar grouping and the portal

   is the first thing a screenshot of the flagship shows and it is a template change, not a renderer change.
9. **#379 — the skip discipline (E14).** It is a rig, so it applies to every scenario #209 will add, and
   Electron's six-of-ninety Wayland job is the strongest available evidence for what happens without it.
10. **#375 — injected coordinates under fractional scale (E10).** It is small, it is invisible until #51 lands,
    and when it does land it turns every e2e press assertion into a silent timeout. Fixing it before the two
    subsystems meet costs an afternoon.
